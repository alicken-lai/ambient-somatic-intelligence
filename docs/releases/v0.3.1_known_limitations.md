## 2. What the Ontology CANNOT Do

| Limitation | Detail | Impact |
|-----------|--------|--------|
| No auto-promotion | All promotions require explicit `governance_decision_id`; system cannot learn autonomously | By design — safety constraint |
| No self-certification for L2+ | `max_self_certification_layer = 1` in `VerificationPolicy` | By design — prevents self-reinforcing errors |
| No corrective action from precursor detection | `PrecursorMatcher` detects and signals but takes no corrective action | Precursors are observation-only |
| No automatic skill routing mutation | `SkillRouter` routing table is static; no mechanism to auto-modify routing conditions | Skills can be added but routes don't self-adjust |
| No live memory mutation from tests | Tests use isolated fixtures; production data is never touched | Tests verify logic, not production state |
| No cross-project validation infrastructure | L3→L4 requires cross-project evidence, but no mechanism exists to share evidence across project boundaries | L4 promotion is currently aspirational |
| No strategic rule conflict detection | No system to detect when two L4 strategic rules contradict each other | Must be built before L4 is fully operational |
| No metacognitive feedback loops | L4 rules cannot yet modify cognitive operation parameters (attention weights, decay rates) at runtime | Phase E in implementation roadmap |

## 4. Schema Inconsistency

### `schema.json` `additionalProperties: false`

**Location:** Project-level `schema.json` (if present in the project root or `architecture/`)

**Problem:** If any JSON schema file uses `additionalProperties: false`, adding new fields to existing schemas will fail validation. The v0.3.1 ontology introduces new fields in:

- `EpisodicEntry` — `layer`, `linked_entries`
- `InstinctEntry` — `contextual_applicability`, `contradiction_count`, `layer`
- `SkillMemoryEntry` — `contexts_validated`, `linked_skill_id`, `layer`
- `StrategicEntry` — `cross_project_validations`, `verifier_id`, `layer`

If these schemas are validated against a strict JSON schema with `additionalProperties: false`, the new fields will be rejected.

**Mitigation:** Ontology schemas use Python dataclass serialization (`to_dict()` / `from_dict()`) which is independent of JSON Schema validation. However, any downstream consumer that validates against a strict JSON schema must be updated.

## 5. Skillify Bugs

### 5.1 Governance Level Mismatch

**Location:** `agents/skillify/skill_candidate_generator.py` vs `skills/core/skill_validator.py`

**Problem:** The `SkillCandidateGenerator` may assign `governance_level = "BLOCK"` to candidates, but `SkillValidator` (line 20-21) only accepts:

```python
VALID_GOVERNANCE_LEVELS = {"ALLOW", "REVIEW_REQUIRED", "BLOCK_WITHOUT_APPROVAL"}
```

A candidate with `governance_level = "BLOCK"` will fail schema validation at registration time with:

```
Invalid governance_level 'BLOCK'; must be one of ['ALLOW', 'BLOCK_WITHOUT_APPROVAL', 'REVIEW_REQUIRED']
```

**Impact:** Skills with destructive operations cannot be registered through the Skillify pipeline until the governance level naming is reconciled.

### 5.2 `_try_skill_registry` Dict vs Typed Objects

**Location:** `agents/skillify/skill_registration_pipeline.py`

**Problem:** When attempting to register a skill from a Skillify candidate, the pipeline constructs `SkillSchema` using raw `dict` objects for `inputs` and `outputs` fields instead of typed `SkillInput` and `SkillOutput` instances.

The `SkillValidator.validate_schema()` method accesses `inp.name` and `out.name` (attribute access) on these dicts, which raises `AttributeError` because dict objects use `dict["name"]` syntax.

**Impact:** Skillify-generated skills may fail at the `register()` stage after passing proposal and approval. The pipeline's propose and approve stages work correctly; only the final registration step is affected.

## 6. Memory Palace Static Nature

**Location:** `mempalace/` directory

**Problem:** The Memory Palace is a pre-built static snapshot. No runtime process updates it, queries it dynamically, or synchronizes it with the live memory ontology.

**Impact:** The Memory Palace does not reflect runtime state changes. It is useful as a reference artifact but does not participate in the live cognitive loop.

## 7. `access_counts.json` Never Populated

**Location:** `state/access_counts.json` (or similar path)

**Problem:** The file exists in the project structure but is never written to by any runtime code. No module calls a function that updates access counts in this file.

**Impact:** Any subsystem that reads `access_counts.json` to make decisions (e.g., popularity-based routing, cache eviction) will always see empty data.

---

## 8. Somatic `episodes.jsonl` Never Created

**Location:** Expected at `memory/somatic/episodes.jsonl`

**Problem:** The `SomaticEpisodeStore` class (`memory/somatic/sensor_episode_store.py`, 302 lines) has full implementation for storing and retrieving episodes, but no runtime process invokes `store()` with real data. The episodes file is never created.

**Impact:** The somatic memory subsystem has complete code but no production data. All somatic episode functionality is testable but not exercised in production.

---

## 9. TemporalContext Uses UTC Not Local Timezone

**Location:** Throughout the ontology and somatic modules — all timestamps use `datetime.now(timezone.utc)` or `datetime.fromisoformat()`

**Problem:** All timestamps are stored in UTC. There is no conversion to the local timezone for display or for timezone-dependent logic (e.g., "was this event during business hours?").

**Impact:**
- Decay calculations are correct (they use elapsed time, which is timezone-invariant)
- However, any human-readable report or UI that displays timestamps will show UTC, which may be confusing for operators in non-UTC timezones
- Any temporal logic that depends on local time-of-day (e.g., attention budget allocation during business hours) would need explicit timezone conversion

---

## 10. `SkillRegistry.load()` Doesn't Restore Execute Callables

**Location:** `skills/core/skill_registry.py` lines 175-202

**Problem:** The `load()` method reads JSONL records and counts them but does NOT reconstruct `SkillSchema` objects or restore the `execute` callable. From the source code:

```python
def load(self, path: Path | str | None = None) -> int:
    """Load registry metadata from JSONL.

    Note: only metadata is loaded — execute callables must be
    re-registered by the skill modules themselves.
    """
```

The method reads lines, parses JSON, and counts records — but never creates `SkillSchema` instances or populates `self._skills`.

**Impact:** After a process restart, `load()` reports how many skills were saved, but the registry remains empty. Skills must be re-registered by their source modules (via `_register_default_skills()` in `boot_v04()`) on every boot.

## 11. No End-to-End L1→L4 Pipeline Test

**Problem:** While individual unit tests cover each component:
- `test_promotion_engine.py` tests promotion logic
- `test_decay_engine.py` tests decay logic
- `test_confidence_model.py` tests confidence updates
- `test_schemas.py` tests serialization

No test exercises the complete production pipeline:

1. Create raw L1 episodic entries from real-world-like data
2. Accumulate enough occurrences to meet L1→L2 threshold
3. Propose promotion to L2 via `PromotionEngine`
4. Submit independent verification via `ConfidenceValidator`
5. Approve promotion with governance decision
6. Continue through L2→L3 with cross-context validation
7. Continue through L3→L4 with verifier approval

**Impact:** Integration bugs between subsystems (e.g., the `SkillInput`/`SkillOutput` dict mismatch in Skillify) can only be caught by manual testing or by reading the code carefully.
